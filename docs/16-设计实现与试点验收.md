## 设计、实现与证据

| 项目 | 设计目标 | 当前实现 | 已验证证据及边界 |
|---|---|---|---|
| 部署架构 | 控制面与数据面分离，服务独立扩容 | `create_app` 装配多个路由；Compose/K8s 基础配置为应用与 Worker；`services/` 为共享代码的模块入口 | 仓库配置可核查；独立服务故障隔离、容量与必要性尚未在目标环境验证 |
| 控制台 | 管理能力、知识与治理；原规划 Vue 3 | 原生 HTML/CSS/JS，由 FastAPI 托管；仅有数据源的指标展示实时值，显示就绪探测与连接状态 | 2026-11-17 隔离本地实例浏览器状态冒烟通过；目标环境表现需逐项验收 |
| 模型 | 私有化推理、OpenAI 兼容及多 LoRA | Mock/代理客户端和网关接口 | 测试覆盖 Mock 及代理接口；真实 vLLM、GPU 和 LoRA 效果、性能需目标环境证据 |
| 知识检索 | 混合检索、审批发布、引用与版本追溯 | 文档、版本、索引、授权、SQL/Milvus 适配和引用接口 | `tests/test_pilot_acceptance.py` 验证合成数据的接口链路；真实语料、Milvus 和检索质量另行验收 |
| 图谱 | Neo4j 辅助检索 | 图存储适配与可选图谱查询 | 仓库已有测试和历史联调记录，目标集群规模、一致性及恢复待验收 |
| 数据治理 | 反馈、标注、数据集版本及评测闭环 | 检索反馈关联原事件和索引，经过人工标注后冻结并评测，支持 Worker | `tests/test_pilot_acceptance.py` 和 `tests/test_feedback_regression.py` 验证本地合成样本；真实司法金标准仍待业务方建立 |
| 安全与可观测 | 权限隔离、脱敏、审计、探测 | 资源 ACL、能力授权、凭证、事件、健康与指标接口；交付环境校验更严格 | 各模块自动测试及 `docs/15-企业级加固验收记录.md` 的历史记录；需真实身份源、权限矩阵、安全审计验证 |
| 高可用和恢复 | 多副本、依赖降级、备份恢复 | Compose/K8s 清单、Worker、备份及就绪探测 | 配置与脚本存在不等于线上已验证；目标环境需实测 RTO/RPO、故障恢复与告警 |

`/readyz` 表示当前配置下的就绪检查，不表示所有未启用依赖均健康，
也不代表功能正确、数据质量达标或满足 SLA。控制台不使用治理事件处理状态推算调用成功率。

## 可重复试点

本地接口回归入口：

```powershell
uv run python -m pytest tests/test_pilot_acceptance.py
```

测试使用独立租户和应用、合成文本、Mock 推理及本地数据库，依次检查：

1. 文档入库并构建索引。
2. 未审批索引不能发布生产别名，审批后发布。
3. 未授权应用不能检索，授权后可以检索。
4. 引用返回文档版本与来源位置，并能读取原始分块。
5. 以检索请求 ID 提交负向反馈，并以同一请求 ID 创建坏案例、加入回归集。
6. 从检索反馈创建待人工审核的数据集，审核通过后发布冻结，并执行基线和候选两次检索评测。

这条测试验证工程流程，测试中的审核由测试代码模拟，不证明法律正确性或真实业务指标达标。
其他基于事件自动生成的数据集仍可能以原检索结果作为相关标签，不能作为独立质量金标准。
业务验收应使用独立标注、经过复核的标准答案及固定版本数据集，并记录样本来源和审核人。
坏案例登记与评测仍是不同入口；可通过以下来源配置显式转换为待审核样本，
不会把坏案例自动视为已审核的金标准。

### 反馈回归接口步骤

以下请求体中的 ID 应替换为前一步实际返回值；调用者需要相应治理权限和知识库、文档访问权。

1. 创建 `type` 为 `RETRIEVAL_EVAL` 的数据集，然后向
   `POST /api/v1/datasets/{dataset_id}/versions` 提交：

   ```json
   {
     "version": "v1",
     "source_snapshot": {"source": "retrieval_feedback", "feedback_ids": [123]},
     "split": {"train": 0, "validation": 0, "test": 1}
   }
   ```

   也可使用 `"source": "retrieval_bad_case"` 和 `"bad_case_ids": [123]`
   选择坏案例。坏案例必须具有请求 ID，且能够唯一关联同租户的检索事件；
   因坏案例未记录应用身份，存在多个匹配事件时会拒绝转换。

2. 通过 `GET /api/v1/dataset-versions/{version_id}/items` 获取待审核样本；
   向 `POST /api/v1/annotation-tasks` 创建任务：

   ```json
   {"name": "反馈审核", "task_type": "RETRIEVAL", "dataset_version_id": 456, "required_reviewers": 2}
   ```

3. 各审核人向 `POST /api/v1/annotation-tasks/{task_id}/records` 提交，例如：

   ```json
   {"item_id": 789, "decision": "APPROVED", "label": {"relevant_chunk_ids": ["原索引中的分块ID"]}}
   ```

   如果人工确认检索不应返回任何结果，标签使用
   `{"relevant_chunk_ids": [], "expect_empty": true}`。评测单独统计
   `empty_samples` 和 `empty_accuracy`，可用 `empty_accuracy` 配置门槛；
   该指标仅衡量检索结果是否为空，不证明生成式回答正确拒答。

   意见不同进入 `CONFLICT`，由未参与该样本审核的独立身份提交
   `decision: "ARBITRATED"` 和最终标签。审核人身份取自认证主体，交付环境要求实名用户。
4. 全部样本通过后，调用 `POST /api/v1/dataset-versions/{version_id}/publish` 冻结。
   然后向 `POST /api/v1/evals` 分别提交基线和候选评测，例如：

   ```json
   {
     "dataset_version_id": 456,
     "target_type": "RETRIEVAL",
     "target_version": "baseline",
     "config": {"top_k": 3, "gates": {"recall_at_k": 0.8}}
   }
   ```

评测结果记录实际使用的知识库及索引版本；`target_version` 只是标识，
不会自动切换索引。比较不同索引时须显式配置版本并核对结果中的实际版本。
创建、审核、发布、导出和执行时会检查资源权限；标注证据必须属于原检索索引快照。
驳回样本会阻止发布；待上一轮任务完成后，可为同一版本创建新的检索审核任务，
重新审核驳回样本。新任务不得降低审核人数，既有审核记录会保留。
也可向 `POST /api/v1/dataset-versions/{version_id}/items/exclude` 提交
`{"item_ids": [789], "reason": "剔除原因"}`。仅允许剔除已驳回项；
剔除记录、原因和原审核记录保留，交付环境需要实名用户。剔除项不参与发布摘要、
导出和评测，全部剔除的版本不能发布。
事件写入为非阻塞操作，缺失或无法唯一关联原事件时，该反馈不能转换为回归样本。
