# 开发与验证记录

> 本记录是阶段性工程证据，不是最终验收报告或生产上线批准。

## 2026-11-06 无容器替代方案（本机无法运行 Docker）

### 背景

开发机没有 Docker，也没有 WSL 发行版；Milvus 官方轻量版（milvus-lite）仅支持
Linux/macOS，Windows 上无法本地启动向量库。因此"起一套 compose 再跑验收"的路径不可用。

### 方案

拆成两层，分别回答不同问题：

1. **契约层（零外部依赖，本机可跑）**
   - `.env.local-staging`：SQLite + SQL 向量 + mock 推理 + 无 Redis（缓存/限流自动退回
     内存），但把 ACL、索引审批、prod alias、相关性阈值等**治理开关全部打开**。
   - `scripts/acceptance/run_staging_acceptance.py --asgi`：进程内直连 ASGI 应用，
     跑 A01/A03/A05，不依赖任何监听端口。
   - `scripts/acceptance/fault_injection_local.py`：A08 的无容器实现。
     用**依赖不可达地址**（127.0.0.1 上无人监听的端口）制造真实连接失败，
     依次注入 redis / graph / inference / vector 四类故障，每次清空
     `get_settings` 与各依赖单例的 `lru_cache` 后重建应用，验证
     "明确失败或已批准降级、不返回 500"，最后恢复配置验证回到 ready。
2. **生产等价层（需要真依赖）**
   - 可用原生安装替代容器：MariaDB zip、Neo4j Community zip（已有 JDK 21）、
     Keycloak zip（OIDC）、Ollama（OpenAI 兼容推理）。
   - **Milvus 是唯一无法在本机替代的组件**：要么连一台 Linux/远程 Milvus，
     要么接受 SQL 向量后端（性能与故障语义都不等价）。

### 本机验证

- `fault_injection_local.py` 全流程 6 阶段（baseline / redis / graph / inference /
  vector / recovered），**10 秒内全部 PASS**，证据落 `evidence/local-faults-<时间戳>/summary.json`。
- 各阶段判定依据：`/readyz` 返回 503 或 `critical_failures` 非空视为"明确暴露"；
  返回 200 且无告警视为**失败**（静默降级）。
- `ruff check scripts`：通过。

### 边界（不得据此签字）

- 只覆盖"依赖不可达"，不覆盖网络抖动、半连接、超时重连；
- 无法验证"恢复后数据一致"——需要真实依赖与真实中断；
- SQL 向量后端与 mock 推理不能作为检索质量与容量结论；
- 因此本方案只把 A08 从"完全不可测"推进到"降级行为可验证"。

## 2026-11-06 staging 联调准备（A01/A03/A05/A08 执行工具）

  `ALLOW_STATIC_ADMIN` 以便自动化验收，其余生产闸门（MySQL、ACL、索引审批、prod alias、

- 新增 `scripts/check_env.py`：在启动前校验 30 项配置，覆盖 `app.py` 的启动闸门与
  "静默降级"开关，输出 PASS/WARN/FAIL 与非 0 退出码，避免"起不来才发现"或"起来了但结论无效"。
- 新增 `scripts/acceptance/run_staging_acceptance.py`：A01/A03/A05/A08 自动判定执行器。
  支持 `--base-url`（目标环境）与 `--asgi`（进程内自检）；证据落 `evidence/<时间戳>/*.json`
  与 `summary.md`，每条步骤带 `request_id` 以便与访问日志、审计表对齐。
- 新增 `scripts/acceptance/fault_injection.ps1`：A08 故障注入编排（healthy → stop → degraded
  → start → healthy），支持 `docker compose` 与 `kubectl scale` 两种目标。
- 新增相关性下限 `RAG_MIN_DENSE_SCORE` / `RAG_MIN_KEYWORD_SCORE`（默认均为 0，不改变
  历史行为）。判定为"dense 达阈值 **或** 关键词达阈值"，两者都低于阈值才丢弃，
  并在 `usage.filtered_low_relevance` 中返回过滤数量。

### 执行中发现并修复的问题

1. **SQL 兜底路径没有相关性阈值**：任意查询（含完全无关的编造条款）都会返回 top_k 条，
   且引用标为 VERIFIED。RRF 归一化后 top1 恒为 0.6，无法作为绝对阈值，因此改为按原始
   `dense` / `keyword` 信号判定，并抽出 `filter_low_relevance()` 便于单测。
2. **关键词豁免不能写成 `keyword > 0`**：`keyword_score` 只要有单个字符重叠就大于 0，
   这样写等于阈值形同虚设；已改为比较可配置阈值（`RAG_MIN_KEYWORD_SCORE`）。
3. **A03 回滚断言方式错误**：由于上面第 1 点，"回滚后结果数为 0" 不成立。正确判据是
   "新版本内容不再出现"，执行器已改为按内容标记判断。
4. **`approve` 在未开启审批时返回 409**：本地（`INDEX_REQUIRE_APPROVAL=false`）索引直接
   READY，执行器改为按索引状态判定为 SKIP 并提示 staging 必须开启审批。

### 本机验证

- `pytest tests/test_relevance_floor.py tests/test_retrieval.py tests/test_pdf_citations.py
  tests/test_document_formats_api.py`：18 passed。
- 进程内自检（`--asgi`，SQLite + mock 推理 + SQL 向量）：
  - A03：索引构建、别名切换、别名回滚全部 PASS。
  - A05：检索命中、引用 VERIFIED、`source_url` 可回溯到同一 chunk、文档版本一致，PASS。
  - 阈值实验：`RAG_MIN_DENSE_SCORE=0.15` 时相关查询命中且无依据查询返回 0 条（PASS）；
    设为 `0.5` 时连 "ALPHA-xxxx" 这类短标记查询也被过滤，证明阈值必须按评测集标定，
    不能照抄经验值。
- `ruff check src scripts`：通过。

### 未执行 / 仍需外部证据

- 上述自检只证明**判定逻辑与接口契约**成立，不证明 staging 达标：真实 Milvus/Neo4j/vLLM/
  MySQL/IdP 下的 A01/A03/A05/A08 必须在目标环境重跑并归档证据。
- 相关性阈值的生产取值必须用评测集标定（`docs/13` 的 Recall@K / 引用准确率），当前 0.15/0.3
  只是起点。

## 2026-11-06 文档解析扩展、引用完整性状态与令牌撤销

### 变更

- 新增 `src/judicial_ai/services/document_parser.py`：按扩展名分派的解析器，覆盖 PDF、DOCX、
  XLSX（zipfile + ElementTree，不引入依赖）、CSV/TSV、HTML（html.parser，跳过
  script/style/head）、Markdown/纯文本；编码按 UTF-8-BOM → UTF-8 → GB18030 → Big5 依次回退。
  旧版 `.doc/.xls/.ppt`、`.pptx`、`.rtf`、`.wps`、`.ofd` 与图片类格式返回 415
  `UNSUPPORTED_FORMAT` 并提示转换或走 OCR，不再使用 `decode("utf-8", errors="ignore")` 把二进制
  静默写入知识库。解析结果写入 `DocumentVersion.parse_status`
  （`PARSED`/`PARTIAL`/`FAILED`）、`parse_error`，解析器名写入文档元数据 `parse_parser`。
- 引用完整性从单一布尔改为三态：`citation_status_for()` 区分 `VERIFIED`（片段可在原文逐字定位）、
  `DEGRADED`（片段无法定位，压缩/改写导致）、`INVALID`（引用指向其他 chunk）与 `NONE`。
  `compress_results()` 在压缩**前**基于原始 chunk 文本校验，非 `VERIFIED` 时回退原文并写入
  `citation.status`；检索响应新增 `citation.status`、`citation.counts`、`citation.review_required`，
  并向 `judicial_citation_integrity_total` 计数、对降级情形打 warning 日志。
- 新增 OIDC 令牌撤销（`specs/target-architecture` T12）：`token_revocation` 表与迁移
  `0012_token_revocation`，支持按 `jti` 精确撤销与按 `subject` 在指定时间点前批量撤销；
  认证链路在验签通过后检查撤销，命中返回 401 `TOKEN_REVOKED`；
  管理端点 `POST/GET /api/v1/admin/token-revocations`、`DELETE .../{id}` 并写审计。
  判定结果带本地缓存，`TOKEN_REVOCATION_CACHE_SECONDS`（默认 15）即撤销生效时间上限，
  设为 0 时每次请求查库。缺失 `iat` 时按 fail-closed 处理。
- 新增 `judicial_document_parse_total{parser,status}` 指标，用于发现解析质量退化。
- 修正参数校验错误响应：pydantic `ctx` 内含 `ValueError` 时 JSON 序列化失败导致 500，
  现统一转换为 JSON 安全值。

## 2026-11-03 请求限制与向量故障处理

### 变更

- 按实际接收字节限制 HTTP 请求体，覆盖无长度、伪造长度和分块请求；保留 413 响应及请求追踪。请求体在进入业务处理前缓冲，峰值内存和慢速上传风险仍需结合网关限制及并发测试评估。
