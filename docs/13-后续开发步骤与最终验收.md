# 司法 AI 中台后续开发步骤与最终验收文档

> 文档状态：计划及验收模板，待业务、技术、安全和运维负责人评审确认  
> 编制日期：2026-11-03  
> 主线建议：先建设安全、可信、可追溯的司法知识检索平台，以合同审查作为受控试点。  
> 说明：本文件中的计划、候选目标、待填写项和验收清单均不表示功能已经完成或验收通过。

## 1. 目标、边界与约束

### 1.1 目标

以一个经过确认的司法知识检索试点为起点，交付可接入、可鉴权、可追溯、可评测、可恢复、可运维的 AI 中台。对开放的业务能力，输出必须能够区分事实、依据、模型生成内容和需要人工判断的部分。

“90 分企业级”在本文中不作为可直接测量的验收分数。是否达到交付标准，以范围、目标环境、量化指标、测试证据、遗留缺陷和签字结果为准。

### 1.2 范围分层

| 范围 | 验收原则 |
|---|---|
| 核心平台：身份与授权、能力网关、知识入库与检索、引用、任务、审计、监控、评测、恢复 | 本次核心交付，必须完成对应验收 |
| 合同审查试点 | 若对试点用户开放，必须完成法律规则、依据、人工复核和场景验收；否则关闭或严格限制入口，并在交付说明中标明未交付 |
| 目标模型、向量库、图数据库、统一身份、生产部署 | 以实际交付架构为准；选入范围的组件必须做真实环境联调，不可用 mock 或健康检查替代 |
| 完整 MCP 互通、LoRA 管理、特定高级模型算法、其他业务应用 | 先逐项确认是否纳入本次交付；纳入则明确协议版本、场景及验收项，未纳入不得宣称已完成 |

原计划包含 Qwen3-8B、多 LoRA、GraphRAG、Forge SDD 和两条业务线接入等目标。它们是否是本次最终交付的强制项，应在范围冻结时逐条确认；未经批准不得自行删减原合同或既有承诺。

### 1.3 执行约束

- 本机开发和验证不使用 Docker。优先使用可隔离的本机服务、独立端口及测试数据库；缺失依赖可评估安装，不能绕过操作系统安全策略。
- 不修改、不停止用户现有服务，不覆盖现有数据；执行迁移、恢复、故障注入和负载测试前，先确认测试目标、权限和隔离措施。
- 目标生产环境验收应使用实际交付架构和生产等价配置。若有依赖不能运行，要记录原因、影响与替代方案；核心验收未通过不能用跳过冒充通过。
- 测试默认使用合成或授权脱敏数据。敏感数据的采集、保存、传输、日志和删除须符合目标环境的安全与合规要求。
- 时间、资源和指标在试点范围及环境明确后估算；不能以模板中的阶段顺序推断确定交付日期。

## 2. 当前基线和风险

| 项目 | 当前判断 | 后续要求 |
|---|---|---|
| 基础能力 | 已有网关、模型代理、知识库、检索、权限、数据治理和任务等实现 | 按实际交付范围逐项核验，不以接口存在视为验收 |
| 文档与版本 | 新知识库版本有解析文本和元数据快照；历史版本能力不同 | 补充原件归档、位置追溯、历史数据迁移与限制说明 |
| 合同审查 | 存在固定利率阈值及简化规则，部分引用失败不阻断结果 | 上线前由法律专业人员确认规则与适用边界；未完成则关闭或限制 |
| 外部依赖 | 曾完成部分本机真实依赖联调；最近一次部分 Milvus 测试跳过 | 在最终代码和目标架构上重新验证全链路，记录版本与证据 |
| 效果与运维 | 有评测、监控和恢复基础，但缺少完整业务质量报告及生产演练 | 建立业务金标准、压测、安全与恢复报告 |

详细状态应在启动阶段重新盘点并附证据；旧测试结果和旧文档可能与当前代码不一致。

## 3. 后续开发步骤

每阶段结束时执行相关自动化测试和回归检查，记录代码版本、测试环境、结果和缺陷。阶段可以适度并行，但不得跳过前置安全条件。

### 阶段 0：冻结试点范围和验收基线

**开发及准备**

1. 选定首个试点用户、业务场景、数据类型、部署位置、并发规模和目标服务清单。
2. 梳理当前功能、演示功能、生产禁用项和已有外部依赖；确认 MCP、LoRA、图谱、合同审查等是否属于必交范围。
3. 约定安全分级、数据来源、保留期限、人工复核责任、量化指标及上线审批流程。
4. 固定隔离测试环境和证据保存位置，确认评测样本来源及专家参与方式。

**交付与退出条件**：形成已确认的范围清单、环境清单、权限矩阵、指标表和风险登记；未确认的事项标为待定，不据此做上线承诺。

### 阶段 1：阻断高风险输出与权限漏洞

**开发**

1. 处理合同审查固定阈值、过度确定的法律表述和引用失败静默降级问题；规则应包含来源、适用条件、生效时间或版本，并支持禁用。
2. 在合同审查开放前完成法律专业审核；依据不足、规则不适用或检索失败时明确提示需要人工复核，不提供无依据的确定性判断。
3. 按租户、应用、知识库、文档和操作建立授权矩阵；覆盖上传、查看、检索、引用、图谱、评测、导出及异步任务。
4. 检查敏感信息在日志、错误消息、审计、缓存和模型请求中的暴露；确定脱敏与数据保留策略。

**退出条件**：高风险入口已修正并审核，或已关闭；授权矩阵覆盖的正向与越权测试通过；无未处理的 P0/P1 安全问题。

### 阶段 2：完善文档资产、解析与引用追溯

**开发**

1. 建设原件安全存储与访问控制，记录来源、文件哈希、版本、上传者、时间和保留策略；上传、替换、删除均留痕。
2. 明确 PDF、DOCX、纯文本及其他纳入范围格式的解析结果、失败原因、重试和状态展示。
3. 为支持的格式建立文本块与原文位置关联；扫描件 OCR、表格和复杂版式按试点范围实现，并明确不支持或低置信度情况。
4. 让引用能够关联文档、对应版本、文本片段及可用的位置；不具备页码或精确定位时明确标识，禁止伪造。
5. 明确旧 `LEGACY` 版本的读取、迁移、重建限制和验证方案。

**退出条件**：试点样本可从检索结果追溯到授权原件及对应版本；受限文档无法通过引用泄漏；解析失败可见、可处理。

### 阶段 3：索引一致性、恢复和性能

**开发**

1. 设计文档版本、索引版本及别名切换流程，保障失败时旧版本可用并可回滚。
2. 处理数据库、向量库、图数据库部分写入失败的状态记录、对账、清理、幂等重试和人工处置。
3. 完善 Worker 心跳、超时、重复执行和服务重启后的处置；明确自动重试和必须人工确认的边界。
4. 根据试点数据规模设计和验证增量索引；无法保证正确性时优先保留可恢复的全量路径。
5. 对已选生产后端进行真实数据写入、查询、删除、重建和故障恢复测试，不以健康检查替代。

**退出条件**：故障注入后无静默丢失和错误版本发布；异常可发现、可对账、可恢复；有量化性能基线和已知限制。

### 阶段 4：业务质量评测与持续改进

**开发**

1. 建立经授权的脱敏评测集，覆盖常见问题、难例、无答案、历史版本、敏感内容和权限边界。
2. 由业务或法律专业人员标注标准答案、相关文档及依据；记录样本来源、版本、标注规范和复核结果。
3. 实现或完善召回、排序、引用准确性、无依据拒答、误报漏报等评测与版本对比。
4. 串联反馈、Bad Case、标注、数据集版本、评测及回归流程；评测数据应有权限控制。
5. 根据报告迭代解析、切分、检索和模型配置，对回退或降级路径同样评测。

**退出条件**：评测集及指标口径经业务确认；核心场景达到双方冻结的目标；报告可复现，新增严重 Bad Case 纳入回归。

### 阶段 5：真实依赖、集成与产品完善

**开发**

1. 按冻结架构联调 MySQL、Redis、Milvus、Neo4j、目标模型及真实身份系统；不适用的依赖记录原因。
2. 验证身份映射、禁用、过期及撤销机制的实际生效范围和延迟；测试模型超时、断流、限流、错误映射和降级。
3. 核实控制台各页面的数据来源，清楚区分真实数据、无数据和演示数据；补齐试点操作中的权限、错误和任务状态。
4. 验证 Python/Java SDK 与真实网关契约。若 MCP 纳入交付，按约定协议版本和传输方式与独立客户端及服务端互通，并测试授权与审计。
5. 如需 OCR、双 LoRA、图谱或其他能力，完成对应生产实现及专项验收；否则清楚限制其对外承诺。

**退出条件**：目标架构中的组件均有真实联调报告；试点用户可完成约定流程；不可用功能没有伪装成可用。

### 阶段 6：安全、性能、恢复和试点验收

**工作**

1. 完成代码质量、依赖安全、认证授权、注入、敏感信息和工具滥用测试；修复并复测缺陷。
2. 在生产等价环境对网关、检索、模型和混合负载压测；记录样本规模、吞吐、延迟、错误率、资源及稳定性。
3. 演练数据库迁移和回滚、备份恢复、依赖中断、服务重启和告警；测量恢复时间和数据丢失范围。
4. 试点用户完成端到端 UAT；整理运行手册、发布及回滚方案、告警和值班交接。
5. 汇总验收证据、遗留问题、风险和签字意见；未满足上线门槛时不得宣布生产验收通过。

**退出条件**：本文件第 5 至 9 节的适用项通过，或按照正式变更流程调整范围；形成可追溯的验收结论。

## 4. 测试与证据规则

### 4.1 测试层次

| 层次 | 必测内容 | 证据 |
|---|---|---|
| 静态与单元 | Ruff、mypy、单元测试、关键异常分支 | 命令、结果、覆盖范围、豁免 |
| 集成与契约 | 实际数据库、缓存、检索后端、模型、身份、SDK；适用时验证 MCP | 组件版本、测试配置、测试报告 |
| HTTP 端到端 | 真实 HTTP 服务、独立 Worker、实际目标依赖组成的完整业务链 | 操作步骤、请求标识、任务、审计和结果 |
| 安全 | 租户及文档隔离、越权、敏感信息、注入、凭证和审计 | 测试矩阵、缺陷、修复及复测 |
| 质量 | 版本化业务样本、人工复核、检索及引用效果、无答案与风险案例 | 数据集版本、评分口径、报告和样本追溯 |
| 性能与稳定性 | 目标硬件、实际模型、预期数据量和并发组合 | 负载模型、P50/P95/P99、吞吐、错误及资源 |
| 恢复与运维 | 迁移回滚、备份恢复、依赖故障、任务恢复和告警 | 演练记录、耗时、数据校验、处置日志 |
| UAT | 真实试点人员完成约定业务流程 | 测试记录、问题清单、业务签字 |

每条验收证据至少记录：执行时间、代码或交付包标识、测试环境及组件版本、数据集版本、执行人、步骤或命令、实际结果、日志或报告位置、缺陷编号、结论。不得在报告中记录明文凭证或未经授权的敏感数据。

### 4.2 本机基础门禁

在项目根目录、已配置的隔离环境中执行；具体命令应根据最终依赖和测试约束调整。

```powershell
uv run ruff check src services tests migrations scripts
uv run mypy src
uv run python -m pytest
```

- 数据库迁移及回滚只允许针对事先确认的隔离测试库执行；不得对用户已有数据库直接演练。
- 测试报告必须列出跳过项及原因。模拟模式、本机小模型或单独健康检查，只能证明对应范围，不能替代真实目标依赖及业务 E2E。
- 原计划中的核心模块覆盖率 80%、其他模块 70% 为历史候选门槛，待范围及统计口径确认；覆盖率不能代替关键风险测试。

## 5. 最终验收场景和通过标准

以下条目默认状态均为“待执行”。如某项与冻结交付范围不适用，需记录审批后的范围依据，不得直接删去结果。

| 编号 | 场景及执行重点 | 通过标准与证据 |
|---|---|---|
| A01 | 创建租户、应用、身份和凭证；注册、发布、授权并调用能力 | 合法调用成功，未授权调用拒绝；权限变更和调用可追溯 |
| A02 | 使用试点纳入的文本/PDF/DOCX/OCR 文件入库 | 原件、哈希、元数据、解析状态及版本一致；失败可见；未支持格式明确拒绝或提示 |
| A03 | 创建知识版本、构建索引、切换别名并回滚 | 检索结果对应指定版本；失败不会静默替换已发布版本；回滚可验证 |
| A04 | 通过真实 HTTP 及 Worker 提交、执行、查询任务 | 状态与实际结果一致；重复提交和重启按约定处理；日志和审计可关联 |
| A05 | 通过网关使用目标模型进行检索及回答 | 返回结果与授权知识库一致；引用可定位到对应版本及可用原文位置；无依据时按约定拒答或提示 |
| A06 | 跨租户、应用、知识库、文档执行列表、详情、检索、图谱、评测和导出 | 未授权访问及间接泄漏用例全部拒绝；授权用例正常；变更有审计 |
| A07 | 禁用身份、撤销授权、测试过期凭证 | 按约定生效机制和时限拒绝访问；异步任务与缓存行为符合已批准策略 |
| A08 | 中断模型、数据库、缓存、向量库或图数据库，按适用架构分别测试 | 有明确错误或已批准的降级；告警有效；恢复后结果和索引一致，无静默数据丢失 |
| A09 | 构造索引部分失败、Worker 超时和重复执行 | 可识别不完整状态；重试或人工处置后不产生错误发布、重复结果或跨版本污染 |
| A10 | 备份并在隔离环境恢复数据，执行迁移及回滚演练 | 核对原件、元数据、权限及可重建索引；实测 RTO/RPO 满足已批准目标 |
| A11 | 评测版本化试点样本，包括无答案及受限内容 | 按冻结口径达到质量门槛；记录样本数、分类结果、失败案例及复核结论 |
| A12 | 试点用户在控制台完成业务流程，查看任务和审计 | 数据来源和状态真实可辨；用户完成约定流程；UAT 问题有结论 |
| A13 | SDK 及约定的 MCP/其他协议互通 | 在约定协议版本和传输方式下与独立客户端/服务端成功交互；鉴权、错误及审计正确 |
| A14 | 合同审查试点，若开放 | 法律专家批准规则、适用条件和提示；依据可核验；依据缺失或规则不适用时正确提示人工复核 |
| A15 | 生产等价负载、稳定性及资源测试 | 实测满足冻结的延迟、吞吐、错误率、并发和稳定性目标，报告包含全部前提 |

建议将 A01 至 A12 串成至少一次完整的 HTTP 端到端演练，覆盖从授权、入库、索引、检索引用、反馈评测到异常恢复；独立断言和故障注入仍需分别执行。

| Redis RTO | ≤ 5 分钟 | 待确认：恢复范围、起止点和目标架构 | 待执行 |
| RPO | 原计划未明确 | 待确认：各数据类型可接受的数据丢失范围 | 待执行 |

对于人工评审指标，需要明确样本量、抽样分层、评分规则、复核机制和争议处理。任何未确定的核心指标均属于验收前待办。

## 7. 安全与上线阻断

下列任何一项存在时，不得给出“生产验收通过”结论：

1. 核心场景存在未关闭的 P0/P1 缺陷，或存在已知越权、敏感数据泄漏、不可追溯的数据损坏。
2. 对外开放的法律审查或类似高风险能力缺少专业审核、适用边界、可靠依据或人工复核路径。
3. 目标架构中的核心依赖、权限隔离、真实模型链路或备份恢复未完成实际验证，或仅有 mock、跳过、健康检查证据。
4. 核心质量和非功能指标尚未约定或未达到批准门槛；试点 UAT 未通过。
5. 安全与合规评审未通过，或没有明确的生产权限、监控告警、故障处置、回滚和值班责任人。
6. 验收证据无法关联最终交付版本，或存在重大未经批准的范围变更。

非核心 P2/P3 问题须记录影响、临时措施、责任人及修复期限，并由有权负责人批准。任何延期均不能覆盖上述生产阻断条件。
