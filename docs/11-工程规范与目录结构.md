# 11 工程规范与目录结构

## 1. 仓库结构

建议采用单仓多服务（Monorepo），便于共享契约、SDK 和部署配置。

```text
judicial-ai-platform/
├── README.md
├── docs/                          # 设计文档、ADR、接口说明
│   ├── 01-项目概述.md
│   ├── 02-总体架构.md
│   └── ...
├── services/
│   ├── gateway/                   # AI 能力网关
│   │   ├── app/
│   │   │   ├── api/
│   │   │   ├── core/

│   │   ├── tests/
│   │   ├── Dockerfile
│   │   └── pyproject.toml
│   ├── admin/                     # 能力注册、租户、应用、配额
│   ├── retrieval/                 # 知识库、召回、Rerank、引用
```

### 1.1 服务内部分层

```text
app/
├── api/              # HTTP/MCP 入口，参数校验，协议转换
├── core/             # 配置、日志、错误、安全、追踪
├── domain/           # 领域模型、业务规则、用例
├── infrastructure/   # 数据库、缓存、消息、外部客户端
└── main.py
```

规则：

- `api` 不直接访问数据库，调用 `domain` 用例。
- `domain` 不依赖框架和具体数据库实现，通过接口注入。
- `infrastructure` 实现仓储、缓存、消息、外部服务客户端。
- 跨服务共享代码放 `packages/common`，但避免共享领域模型。

## 2. 技术栈与版本

| 类别 | 选型 | 版本策略 |
|---|---|---|
| 语言 | Python | 3.11+ |
| Web 框架 | FastAPI | 固定小版本，按月升级 |
| ORM | SQLAlchemy 2.0 | 固定小版本 |
| 迁移 | Alembic | 与代码同仓 |
| 校验 | Pydantic v2 | 固定小版本 |
| HTTP 客户端 | httpx | 固定小版本 |
| 测试 | pytest + pytest-asyncio + Testcontainers | 固定小版本 |
| 静态检查 | ruff + mypy | 固定版本 |
| 前端 | Vue 3 + TypeScript + Element Plus | 锁定 lockfile |
| 构建 | Docker BuildKit | 多阶段构建 |
| 编排 | Kubernetes + Helm | 固定 API 版本 |
| 推理 | vLLM | 固定镜像 digest |
| 向量库 | Milvus | 固定小版本 |
| 图库 | Neo4j | 固定小版本 |
| 数据库 | MySQL 8.0+ | 固定小版本 |
| 缓存 | Redis 7.x | 固定小版本 |

要求：

- 生产镜像使用 digest 固定，不使用 `latest`。
- 依赖锁定（`uv.lock`/`poetry.lock`/`package-lock.json`）。
- 每月做一次依赖升级与漏洞扫描。
- 升级 vLLM/CUDA/驱动需单独评审和回归。

## 3. 分支与提交

### 3.1 分支策略

- `main`：可发布分支，保护，禁止直接推送。
- `feature/<ticket>-<slug>`：功能分支，短生命周期。
- `fix/<ticket>-<slug>`：缺陷修复。
- `release/<version>`：发布准备（按需）。
- `hotfix/<version>`：紧急修复。

要求：

- 分支从 `main` 拉出，合并前 rebase。
- PR 必须关联需求/任务编号。
- PR 变更行数建议 ≤ 400 行，超过需拆分。
- 合并方式使用 Squash Merge，保持线性历史。

### 3.2 提交信息

采用 Conventional Commits：

```text
feat(gateway): add capability version routing
fix(retrieval): apply tenant filter before recall
docs(adr): add milvus collection design
test(governance): cover dedup pipeline
chore(ci): pin vllm image digest
```

类型：`feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`build`、`ci`、`chore`、`revert`。

### 3.3 代码评审

- 至少 1 名同模块 reviewer；核心模块 2 名。
- 安全相关变更必须有安全评审。
- 评审关注：正确性、安全、数据、性能、并发、可观测、测试。
- 禁止自我合并；紧急修复也需事后补评审。
- 所有评论需解决或明确标记为后续任务。

## 4. 代码规范

### 4.1 Python

- 使用 `ruff format` 和 `ruff check`。
- 类型注解覆盖公共函数和领域模型；`mypy` 严格模式。
- 命名：模块/函数/变量 `snake_case`，类 `PascalCase`，常量 `UPPER_CASE`。
- 异常：定义领域异常，统一映射为 API 错误码；禁止裸 `except`。
- 日志：结构化日志，禁止拼接敏感信息。
- 配置：Pydantic Settings，启动时校验。
- 数据库：仓储模式，禁止在 API 层写 SQL。
- 时间：统一 UTC，接口转换时区。
- ID：雪花 ID/号段，禁止依赖自增。
- 并发：明确超时、取消、重试和幂等。
- 资源：使用上下文管理器，确保连接/文件释放。

### 4.2 TypeScript/Vue

- 使用 ESLint + Prettier。
- 组件使用 `<script setup lang="ts">`。
- API 类型由 OpenAPI 生成，禁止手写重复类型。
- 状态管理按页面/模块拆分，避免全局大 store。
- 权限指令/路由守卫统一封装。
- 错误提示统一组件，避免散落 `alert`。

### 4.3 SQL

- 表名/字段名小写蛇形。
- 所有查询必须带租户条件（除全局表）。
- 禁止 `SELECT *` 用于生产查询。
- 分页查询必须有稳定排序。
- 大表变更使用在线 DDL。
- 迁移脚本命名：`YYYYMMDDHHMM_<description>.sql`。

## 5. API 规范

1. 契约优先：先写 OpenAPI，再实现。
2. 路径使用名词复数：`/capabilities`、`/knowledge-bases`。
3. 动作用 POST/PATCH，避免在 URL 中使用动词（除 `/invoke`、`/search` 等明确动作）。
4. 错误使用统一错误码，不暴露内部异常。
5. 分页、排序、过滤参数统一命名。
6. 所有接口返回 `request_id`。
7. 破坏性变更升级主版本，保留过渡期。
8. 新增字段向后兼容；删除字段需公告。
9. 流式接口使用 SSE，定义 `[DONE]` 和错误事件。
10. 幂等写操作支持 `Idempotency-Key`。

### 5.1 OpenAPI 管理

- `packages/contracts/openapi/*.yaml` 为唯一契约源。
- CI 执行 lint、breaking change 检查。
- SDK 由契约生成，禁止手写漂移。
- 契约变更需评审并通知调用方。

## 6. 测试规范

### 6.1 目录

```text
tests/
├── unit/                 # 领域逻辑
├── integration/          # 数据库/缓存/中间件
├── contract/             # OpenAPI/MCP 契约
├── e2e/                  # 端到端
├── performance/          # 压测脚本
└── security/             # 安全用例
```

### 6.2 要求

- 新增功能必须包含单元测试和至少一个集成测试。
- Bug 修复必须先写复现测试。
- 测试命名：`test_<behavior>_<condition>_<expected>`。
- 测试数据使用 fixture/factory，禁止共享可变状态。
- 集成测试使用 Testcontainers，不依赖本地手工环境。
- 性能测试脚本入库，参数化数据分布。
- 安全测试覆盖越权、注入、敏感信息、工具滥用。

### 6.3 覆盖率

- 核心模块 ≥ 80%，其他 ≥ 70%。
- 覆盖率不达标阻断合并（可按模块配置例外）。
- 覆盖率不是唯一标准，关键分支必须有断言。

## 7. CI/CD

### 7.1 CI 流水线

```yaml
stages:
  - lint
  - typecheck
  - unit-test
  - integration-test
  - contract-test
  - security-scan
  - build
  - publish
```

要求：

- 每次 PR 运行 lint、typecheck、unit、integration、contract、secret scan。
- 主分支运行完整测试和安全扫描。
- 构建镜像生成 SBOM，签名后推送。
- 失败快速反馈，日志可下载。
- 缓存依赖，目标 CI 时长 ≤ 15 分钟。

### 7.2 CD 流水线

- `dev`：自动部署。
- `test`：自动部署 + 集成测试。
- `staging`：手动触发 + 审批。
- `prod`：手动触发 + 变更单 + 审批 + 灰度。
- 部署使用 Helm/Kustomize，配置来自 GitOps。
- 部署后自动冒烟测试，失败自动回滚。

### 7.3 环境与密钥

- CI 使用短期凭证/OIDC，不存长期密钥。
- 生产部署凭证仅限发布机器人。
- 密钥通过 Vault/KMS 注入，不写入日志。
- 构建产物签名，部署时校验。

## 8. 配置管理

- 配置项集中定义，带类型、默认值、说明、校验。
- 环境差异通过环境变量/ConfigMap 注入。
- 动态配置（路由、限流、检索）通过控制面管理，带版本和审计。
- 配置变更支持灰度和回滚。
- 禁止在代码中硬编码地址、密钥、租户 ID。

## 9. 日志、错误与追踪

### 9.1 日志

```json
{
  "timestamp": "2026-10-19T10:00:00.123+08:00",
  "level": "INFO",
  "service": "gateway",
  "request_id": "req-001",
  "trace_id": "trace-001",
  "tenant_id": 1001,
  "app_id": 2001,
  "capability": "llm.qwen3.chat",
  "message": "request completed",
  "latency_ms": 1832,
  "status": 200
}
```

要求：

- 使用结构化日志，禁止多行拼接。
- 敏感字段脱敏；不记录完整 Prompt/输出。
- 错误日志包含错误码、上下文、可重试性。
- 日志级别可动态调整，但生产默认 INFO。

### 9.2 错误

- 领域异常与 API 错误码分离。
- 错误消息面向用户，详细信息进日志。
- 不暴露堆栈、SQL、上游地址、密钥。
- 可重试错误标记 `retryable=true`。

### 9.3 追踪

- 入口生成/透传 `trace_id`。
- 跨服务使用 W3C Trace Context。
- 关键 span：认证、鉴权、路由、上游调用、数据库、检索、Rerank、工具。
- 敏感内容不入 span。

## 10. 文档规范

- 设计文档与代码同仓，变更随 PR 更新。
- ADR 一页一决策，包含背景、选项、结论、代价。
- API 文档由 OpenAPI 生成，不手写重复内容。
- Runbook 包含现象、排查、处置、验证、升级路径。
- 文档使用中文，术语与 [01-项目概述](01-项目概述.md) 保持一致。
- 文档链接使用相对路径，确保可移植。

## 11. Definition of Done

一个任务完成必须满足：

- [ ] 代码实现符合 Spec/Design。
- [ ] 单元测试、集成测试通过，覆盖率达标。
- [ ] OpenAPI/SDK/数据库迁移已更新。
- [ ] 错误码、日志、指标、Trace 已补充。
- [ ] 安全评审通过（涉及权限/数据/工具时）。
- [ ] 文档/ADR/Runbook 已更新。
- [ ] 代码评审无 P0/P1 问题。
- [ ] CI 全绿，镜像可构建。
- [ ] 验收标准逐条有证据。
- [ ] 变更已记录到 CHANGELOG。

## 12. 验收标准

1. 仓库结构、分层、命名符合本文档。
2. CI 覆盖 lint、类型检查、单测、集成、契约、密钥扫描。
3. 核心模块覆盖率 ≥ 80%，其他 ≥ 70%。
4. OpenAPI 为唯一契约源，SDK 自动生成。
5. 所有服务输出结构化日志并透传 Trace。
6. 配置与密钥分离，无硬编码敏感信息。
7. 分支保护、PR 模板、评审规则生效。
8. 部署流水线支持开发/测试/预发/生产，生产变更可审批、可回滚。
9. Definition of Done 被团队执行并有检查记录。
10. 文档与代码同步更新，关键决策有 ADR。
